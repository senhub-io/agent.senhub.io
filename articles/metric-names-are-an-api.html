Metric names are an API

13 October 2026 Shipped in 0.6.1

We ran promtool check metrics against our own output. It failed. Fixing it meant renaming series our users had already built dashboards on — and doing it without a transition period.

A metric name is not a label. Once it is exported, it is in somebody's dashboard, somebody's alert rule, somebody's recording rule, and — if they poll us with Zabbix — in the key of an item that has been collecting history for months. It behaves like a published interface, which means it has the one property interfaces have: changing it costs other people work.

That is a good reason to get it right early, and a bad reason never to fix it.

What the linter found

Prometheus ships promtool check metrics, which reads an exposition and complains about names and units that break the convention. We pointed it at 0.6.0, the release we had just shipped. Three families of problem came back.

Units that were not base units. Durations were exported in milliseconds, microseconds, nanoseconds, hours — and, for the HTTP check's certificate expiry, in days. Throughputs were exported in bits per second. Prometheus and OpenTelemetry both ask for seconds and bytes, and for a good reason: when the unit is implicit in the name, a dashboard built against one exporter transfers to another. When it is not, every panel carries its own invisible multiplication.

Gauges wearing a counter's suffix. Prometheus reserves the .total suffix for counters — monotonic series you take a rate() of. We had gauges ending in it. The clearest case: senhub_veeam_jobs_total was the number of jobs that exist, a value that goes up and down, and every tool in the chain read it as a counter. A rate() over it is not approximately right; it is meaningless.

Names that said the unit twice, or wrongly. senhub_redis_cmd_usec_microseconds_total is the kind of thing that happens when a name grows one commit at a time.

0.6.00.6.1
senhub.veeam.jobs.totalsenhub.veeam.job.count
senhub.citrix.machines.totalsenhub.citrix.machine.count
ceph.osd.totalceph.osd.count
senhub_redis_cmd_usec_microseconds_totalsenhub_redis_cmd_time_seconds_total

No transition period

The tempting answer is to export both names for a while. We decided against it, and the reason is worth stating plainly: a dual-name period doubles the series count for everyone, doubles the surface we have to keep correct, and — in our experience of watching other projects do it — nobody migrates until the old name disappears. It converts a one-off cost into a permanent one.

So 0.6.1 renames, and the upgrade asks for work: dashboards, alerts and recording rules built on the old names have to be updated. The release note carries the full table rather than a summary, because a partial list is worse than none.

A name that is wrong is not a cosmetic problem. It is a tool reading your data backwards and telling you nothing is wrong.

What it did not touch

PRTG and Nagios are unaffected. They keep their channel names and the probe's display unit, because those are presentation surfaces where the unit is shown next to the value rather than carried by the name. The convention we were failing is a Prometheus and OpenTelemetry convention; applying it where it does not belong would have been its own kind of wrong.

Zabbix sits in between. Its item keys are built from the metric names and its values from these units, so the keys changed with them. Re-running senhub-agent zabbix setup after the upgrade refreshes the templates. The old items do not vanish — they keep their history and stop receiving, which is the failure mode worth knowing about: nothing errors, the curves simply stop.

The part that generalises

Running the ecosystem's own linter against your own output is cheap, and we had not done it. It took one command to find a year of accumulated drift, and the drift was invisible from the inside: every name looked reasonable next to the code that produced it. It only looked wrong next to the convention.

If you export metrics, point promtool check metrics at yourself before your users do.

Everything above is in the 0.6.1 release note, including the complete table of renamed series and the units that changed, probe by probe.
